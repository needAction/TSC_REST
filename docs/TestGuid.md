# 두 PC 클라이언트 빌드 테스트 가이드

작성일: 2026-10-15  
대상: Unity 6 클라이언트 + 로컬 Docker 서버 + Vivox 자동 음성 연결

## 1. 테스트 목표와 진행 순서

새 Windows 빌드에서 두 참가자의 입장, 자동 씬 준비 보고, 양방향 음성, 정상 퇴장, 재입장, 강제 종료 후 자리 정리, 서버 중단 알림을 확인합니다.

순서는 **서버 접근 확인 → 빌드 준비 → 한 명 입장 → 두 명 입장 → 음성 → 정상 퇴장·재입장 → 강제 종료 → 서버 중단·복구**입니다.

앞 단계가 통과하면 다음 단계로 진행합니다. 실패하면 해당 테스트 번호, 화면 안내, 로그를 먼저 기록합니다. 이번 문서의 결과란은 새 빌드로 검사한 뒤 작성합니다.

## 2. 테스트 환경과 사전 준비

### PC 구분

| 이름 | 역할 |
|---|---|
| PC A | Docker 서버와 첫 번째 게임 클라이언트 실행 |
| PC B | 같은 서버에 접속하는 두 번째 게임 클라이언트 실행 |

PC A에서 먼저 입장하면 게임 역할 A, PC B에서 다음으로 입장하면 게임 역할 B를 받습니다. 여기서 PC 이름과 게임 역할은 별개이며, 실제 역할은 입장 순서와 빈자리에 따라 결정됩니다.

### 준비 체크리스트

- [ ] PC A와 PC B가 서로 통신할 수 있는 네트워크에 연결되어 있습니다.
- [ ] 두 PC 모두 인터넷에 연결되어 있습니다. 음성은 Vivox 서비스를 사용합니다.
- [ ] 두 PC의 마이크와 이어폰 또는 헤드셋을 확인했습니다.
- [ ] PC A에 Docker Desktop/Engine이 설치되어 있고 Linux 컨테이너 엔진이 실행 중입니다.
- [ ] 배포 실행 파일에 필요한 Node.js 24 이상과 Docker CLI가 PC A에 있습니다.
- [ ] 서버의 `.env.deploy-local`과 `.env.docker-test`가 준비되어 있습니다. 파일이 없다면 대응하는 `.example`을 복사합니다.
- [ ] 클라이언트의 Unity Cloud 프로젝트 및 Vivox 설정이 기존 검증한 설정으로 연결되어 있습니다.
- [ ] 검사 전에 Unity 재생 모드를 종료했습니다. 빌드 실행 파일은 PC마다 하나씩 실행합니다.

서로 가까운 PC에서는 스피커 소리가 다른 마이크에 다시 들어갈 수 있으므로 이어폰/헤드셋을 사용하면 음성 방향을 확인하기 쉽습니다.

## 3. T01 — 최신 서버 실행과 두 PC의 접근 확인

### 진행 방법

1. PC A에서 Docker Desktop을 실행합니다.
2. 서버 프로젝트의 [run-docker-local.cmd](../run-docker-local.cmd)를 실행합니다. Linux에서 서버를 실행한다면 `sh run-docker-local.sh`를 사용합니다.
3. 빌드, 서버 설정 검증, 컨테이너 교체와 상태 확인이 끝날 때까지 기다립니다.
4. 마지막에 아래와 같은 완료 메시지가 나오는지 확인합니다.

```text
[배포 완료] escape-server-lan-test / http://127.0.0.1:3001/health → status: ok
```

5. PC A의 PowerShell에서 `ipconfig`를 실행합니다. 현재 사용 중인 Wi-Fi 또는 이더넷의 IPv4 주소를 기록합니다.
6. 두 PC의 브라우저에서 다음 주소를 각각 확인합니다.

| 확인 PC | 주소 |
|---|---|
| PC A | `http://127.0.0.1:3001/health` |
| PC B | `http://PC_A의실제IPv4주소:3001/health` |

### 통과 기준

- [ ] 배포 완료 메시지가 표시됩니다.
- [ ] PC A의 `/health` 응답이 `{"status":"ok"}`입니다.
- [ ] PC B의 `/health` 응답도 `{"status":"ok"}`입니다.

PC B에서 접근되지 않으면 서버 주소, 같은 네트워크 여부, PC A의 방화벽에서 TCP 3001 접근이 허용되는지 확인합니다. 서버 접근이 확인된 뒤 게임 입장 검사를 진행합니다.

기본 포트 구성은 **PC A의 3001 → 컨테이너 내부 3000**입니다. 배포 설정에서 호스트 포트를 변경했다면 이 문서의 접속 주소도 해당 포트로 바꿉니다.

## 4. 새 Windows 클라이언트 빌드

### Unity에서 준비

1. `SampleScene`을 저장하고 재생 모드를 종료합니다.
2. **File → Build Profiles**를 엽니다.
3. Windows 플랫폼과 64비트 구성을 선택합니다.
4. 사용할 프로파일의 씬 목록에서 `Assets/1.Scene/SampleScene.unity`가 활성화되어 있고 첫 번째인지 확인합니다.
5. 이번 검사에서는 **Development Build**를 켭니다.
6. 새 출력 폴더를 지정하고 빌드합니다.

현재 프로젝트의 공통 빌드 씬 목록은 SampleScene이 첫 번째입니다. 개별 프로파일이 자체 씬 목록을 사용하는 경우 해당 목록도 확인합니다. 빌드 프로파일의 메뉴와 설정은 [Unity 6.2 공식 안내](https://docs.unity3d.com/6000.2/Documentation/Manual/build-profiles.html)를 참고할 수 있습니다.

### PC B에 전달

빌드 출력 폴더 전체를 PC B에 복사합니다. 실행 파일과 함께 `_Data` 폴더, `UnityPlayer.dll` 등 빌드에 포함된 파일이 필요합니다. [Unity Windows 빌드 안내](https://docs.unity3d.com/6000.2/Documentation/Manual/WindowsStandaloneBinaries.html)

- [ ] 빌드가 오류 없이 완료됐습니다.
- [ ] 같은 새 빌드 폴더를 PC A와 PC B에 준비했습니다.
- [ ] 두 PC에서 실행했을 때 서버 주소 입력창, 입장 버튼, 게임 상태와 음성 상태 표시가 보입니다.

현재 입력창 기본 주소는 `http://127.0.0.1:3000`입니다. **이번 Docker 검사에서는 주소와 포트를 아래와 같이 입력합니다.**

| 클라이언트 위치 | 입력할 주소 |
|---|---|
| PC A | `http://127.0.0.1:3001` |
| PC B | `http://PC_A의실제IPv4주소:3001` |

## 5. T02 — 첫 번째 참가자 입장

### 진행 방법

1. PC A의 게임에 서버 주소를 입력합니다.
2. PC A에서만 **입장**을 누릅니다.
3. 게임 상태와 음성 연결이 표시될 때까지 기다립니다.

### 통과 기준

| 항목 | 정상 결과 | 확인 |
|---|---|---|
| 게임 상태 | 상대방 입장 대기 | [ ] |
| 게임 역할 | A | [ ] |
| 참가자 수 | 1 | [ ] |
| 음성 상태 | 연결 중을 거쳐 `음성: 연결됨 (1명)` | [ ] |
| 버튼 | 나가기 | [ ] |

음성 참가자 수에는 본인이 포함됩니다. 한 명만 입장한 시점의 1명 표시는 정상입니다.

## 6. T03 — 두 번째 참가자 입장과 자동 플레이 전환

### 진행 방법

1. PC A는 접속 상태를 유지합니다.
2. PC B에 PC A의 실제 IPv4 주소와 3001 포트를 입력하고 **입장**을 누릅니다.
3. 두 PC의 준비 보고와 자동 조회가 진행되도록 기다립니다.

### 통과 기준

| 항목 | PC A | PC B | 확인 |
|---|---|---|---|
| 게임 상태 | 플레이 중 | 플레이 중 | [ ] |
| 게임 역할 | A | B | [ ] |
| 참가자 수 | 2 | 2 | [ ] |
| 음성 상태 | 연결됨 (2명) | 연결됨 (2명) | [ ] |

씬과 필수 객체의 준비를 확인하면 로딩 완료 보고가 자동으로 전송됩니다. 사용자가 Report Scene Loaded를 수동으로 실행할 필요는 없습니다. 중간 로딩 상태는 빠르게 지나갈 수 있습니다.

게임과 음성은 별도 상태입니다. 게임이 플레이 중이어도 음성이 실패로 표시되면 음성 검사는 아직 통과한 것이 아닙니다.

## 7. T04 — 실제 양방향 음성 송수신

### 진행 방법

1. PC A에서 “A에서 말합니다”라고 말하고 PC B에서 들리는지 확인합니다.
2. PC B에서 “B에서 말합니다”라고 말하고 PC A에서 들리는지 확인합니다.
3. 잠시 대화하면서 한쪽만 들리거나 소리가 끊기는지 확인합니다.

### 통과 기준

- [ ] A → B 방향의 목소리가 들립니다.
- [ ] B → A 방향의 목소리가 들립니다.
- [ ] 두 화면의 음성 상태가 연결됨 (2명)을 유지합니다.

참가자 수가 2명으로 표시되는 것과 실제 목소리가 들리는 것은 각각 확인합니다.

## 8. T05 — 정상 퇴장

### 진행 방법

1. 두 PC가 플레이 중이고 음성 연결도 완료된 상태에서 시작합니다.
2. PC B의 게임 안에서 **나가기** 버튼을 누릅니다.
3. 퇴장 요청과 음성 정리, PC A의 다음 상태 조회가 완료될 때까지 기다립니다.

### 통과 기준

| 위치 | 정상 결과 | 확인 |
|---|---|---|
| PC B | 접속 전, 음성 접속 대기, 입장 버튼 | [ ] |
| PC A | 상대방 입장 대기, 게임 참가자 1명 | [ ] |
| PC A 음성 | 연결됨 (1명) | [ ] |
| PC B 알림 | 정상 퇴장으로 연결 끊김 팝업이 발생하지 않음 | [ ] |

서버가 정상 응답한 퇴장에서는 자리를 즉시 제거합니다. PC A의 화면은 다음 조회와 음성 이벤트를 받으면 갱신됩니다.

## 9. T06 — 정상 퇴장 후 재입장

### 진행 방법

1. PC A는 접속을 유지합니다.
2. PC B에서 다시 **입장**을 누릅니다.
3. 자동 준비 보고와 음성 연결을 기다린 뒤 양방향으로 말해 봅니다.

### 통과 기준

- [ ] PC B가 SESSION_FULL 오류 없이 입장합니다.
- [ ] 두 PC 모두 플레이 중, 게임 참가자 2명입니다.
- [ ] 두 PC 모두 음성 연결됨 (2명)입니다.
- [ ] 양방향 음성이 다시 들립니다.

재입장은 새 참가자 ID와 토큰을 받는 신규 입장입니다. 이전 참가자 신분을 복구하는 기능과 구분합니다.

## 10. T07 — 강제 종료 후 만료와 새 참가자 입장

### 진행 방법

1. 두 PC가 플레이 중이고 음성이 연결된 상태에서 시작합니다.
2. PC B에서 작업 관리자를 열어 게임 프로세스를 종료합니다.
3. PC A를 실행한 채 약 10~15초 기다립니다.
4. PC A의 게임 참가자 수가 1명으로 바뀌었는지 확인합니다.
5. PC B의 게임을 다시 실행하고 같은 서버에 입장합니다.
6. 두 PC의 게임 상태와 양방향 음성을 확인합니다.

### 통과 기준

- [ ] 강제 종료 후 PC A가 상대방 입장 대기, 참가자 1명으로 바뀝니다.
- [ ] PC B의 새 입장이 SESSION_FULL 오류 없이 성공합니다.
- [ ] 두 PC 모두 플레이 중, 게임 참가자 2명으로 돌아옵니다.
- [ ] 음성이 2명으로 연결되고 양방향 송수신이 됩니다.

서버의 만료 기준은 **마지막 생존 확인 수신 이후 10000ms**입니다. 주기 검사와 화면 조회가 이어지므로 관찰할 때는 약 10~15초 기다립니다. OS나 네트워크가 지연되는 경우 실제 표시 시각은 달라질 수 있습니다.

강제 종료된 사용자의 Vivox 참가자 정리는 별도 서비스의 연결 감지 시간에 따릅니다. 게임 참가자 만료 시각과 음성 인원 감소 시각이 정확히 같다고 판단하지 않습니다.

## 11. T08 — 서버 중단 알림과 서버 복구 후 새 입장

### 진행 방법

1. 두 PC가 플레이 중이고 음성이 연결된 상태에서 시작합니다.
2. PC A의 Docker Desktop에서 `escape-server-lan-test` 컨테이너를 **Stop**합니다.
3. 두 게임을 실행한 채 약 10~15초 기다립니다.
4. 두 PC에서 연결 종료 알림과 음성 정리를 확인하고 알림의 확인 버튼을 누릅니다.
5. Docker Desktop에서 같은 컨테이너를 다시 **Start**합니다.
6. PC A와 PC B의 브라우저에서 `/health` 응답을 다시 확인합니다.
7. 두 PC에서 차례로 **입장**을 누른 뒤 게임과 양방향 음성을 확인합니다.

### 통과 기준

- [ ] 서버 중단 후 두 PC에 연결 종료 알림이 표시됩니다.
- [ ] 두 PC의 음성이 접속 대기로 바뀌며 기존 음성 연결이 정리됩니다.
- [ ] 알림 확인 후 입장 버튼을 사용할 수 있습니다.
- [ ] 서버 복구 후 두 PC의 `/health`가 정상 응답합니다.
- [ ] 새 입장 후 두 PC가 플레이 중, 참가자 2명, 음성 2명이 됩니다.
- [ ] 양방향 음성이 다시 들립니다.

클라이언트 연결 종료 기준은 마지막 정상 생존 확인 응답 이후 10000ms입니다. 서버를 다시 시작하면 기존 메모리 세션과 토큰이 초기화되므로, 서버 복구 후에는 사용자가 새로 입장합니다.

| PC A의 health도 실패 | 배포 완료 여부, Docker 컨테이너 실행 상태, 공개 포트 |
| PC A는 성공하고 PC B만 health 실패 | PC A의 실제 IPv4 주소, 같은 네트워크 여부, 방화벽 TCP 3001 |
| 게임이 서버에 연결되지 않음 | 입력창의 주소와 Docker 호스트 포트 3001 |
| 참가 인원이 가득 찼다고 표시 | 추가 실행 중인 클라이언트, 기존 참가자의 만료 대기 여부 |
| 두 명인데 플레이 중으로 바뀌지 않음 | SampleScene과 자동 씬 준비 보고, 빌드 로그 |
| 음성 1명 또는 로그인·입장 실패 | 동일 서버·세션과 Cloud 프로젝트 설정, 인터넷, 음성 오류 문구 |
| 음성 2명인데 들리지 않음 | 각 PC의 마이크·출력 장치 선택, OS 마이크 접근 권한, 음량 |
| 서버 응답 처리 오류 | 서버와 클라이언트의 최신 코드·새 이미지·새 빌드 사용 여부 |

### 클라이언트 로그

현재 프로젝트의 Company Name은 DefaultCompany, Product Name은 listen입니다. 각 Windows PC에서 다음 경로를 확인합니다.

```text
%USERPROFILE%\AppData\LocalLow\DefaultCompany\listen\Player.log
```

Company Name이나 Product Name을 변경했다면 해당 폴더명도 달라집니다. 재실행 전에 오류가 발생한 Player.log를 별도로 복사하면 당시 기록을 보존할 수 있습니다.

### 서버 로그

PC A의 Docker Desktop에서 `escape-server-lan-test`를 선택하고 Logs를 확인합니다. 배포 실행 파일이 출력한 빌드·설정·health 오류도 함께 기록합니다.

### 오류 전달 양식

```text
테스트 번호:
발생 PC: A / B
직전에 한 동작:
예상 결과:
실제 게임 상태 / 참가자 수:
실제 음성 상태 / 참가자 수:
화면 오류 문구:
발생 시각:
해당 시각 전후 Player.log 또는 서버 로그:
```
